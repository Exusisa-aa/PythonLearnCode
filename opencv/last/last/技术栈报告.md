## 一、项目概览

一个基于**百度智能云人脸识别 API** 的桌面应用，实现人员的**注册、识别、陌生人判断**与**人脸库管理**。

### 必做功能与实现位置

| #   | 必做功能                 | 实现位置                                                        |
| --- | -------------------- | ----------------------------------------------------------- |
| 1   | 人员注册（输入姓名、采集人脸、保存特征） | [ui/register_tab.py](ui/register_tab.py)                    |
| 2   | 单人识别（输出最相似人员与相似度）    | [ui/recognize_tab.py](ui/recognize_tab.py)                  |
| 3   | 陌生人判断（相似度低时显示陌生人）    | [ui/recognize_tab.py](ui/recognize_tab.py) `_show_stranger` |
| 4   | 人脸库（查看、删除已注册人员）      | [ui/faceset_tab.py](ui/faceset_tab.py)                      |
| 5   | 简单界面（注册/识别/查看结果）     | [ui/main_window.py](ui/main_window.py) + Tkinter            |
| 6   | 陌生人判断（重复强调）          | 同 #3，含"无候选"与"低于阈值"两条分支                                      |

### 运行方式

```bash
pip install -r requirements.txt
cp .env.example .env          # 填入百度 AK/SK
python app.py
```

### 3.3 三条核心数据流

**注册流程**

```
用户输入姓名
  → 本地校验（非空 / ≤256 字节）        register_tab._validate_name
  → 取图（摄像头抓拍 或 选择文件）        preview.current_frame
  → 派生 user_id                        identity.derive_user_id
  → [工作线程] POST /faceset/user/add    baidu_client.add_user
  → [工作线程] 照片落盘 data/faces/       images.save_bgr_image
  → [工作线程] 写本地 SQLite             database.upsert_person
  → [主线程] 弹出成功提示、刷新状态栏      run_in_background 回调
```

**识别流程**

```
取图 → [工作线程] POST /search（阈值透传）
     → 云端比对并返回 user_list（含 score）
     → 取 score 最高的候选
     → score ≥ 阈值 ? 显示姓名+相似度 : 显示"陌生人"
```

**删除流程**

```
选中人员 → 二次确认
  → [工作线程] POST /faceset/user/delete
       ├─ 成功        → 删本地档案 + 删照片文件
       ├─ 用户不存在   → 同样清本地（视为已删）
       └─ 网络/配额失败 → 保留本地档案，报错让用户重试
```

### 4.1 `config.py` — 配置加载与校验（109 行）

**职责**：把 `.env` 里的字符串读成强类型的 `Config` 对象，并在**启动阶段**就把非法配置拦住。

#### 代码段 1：路径常量

```python
BASE_DIR = Path(__file__).resolve().parent
DATA_DIR = BASE_DIR / "data"
PHOTO_DIR = DATA_DIR / "faces"
DB_PATH = DATA_DIR / "faces.db"
```

以**本文件所在目录**为基准而非当前工作目录（`os.getcwd()`），因此 `python app.py`、`python core/database.py`、从 IDE 的运行按钮启动，得到的路径完全一致。

#### 代码段 2：冻结的配置对象

```python
@dataclass(frozen=True)
class Config:
    api_key: str
    secret_key: str
    group_id: str
    match_threshold: int
    quality_control: str
    liveness_control: str
    db_path: Path
    photo_dir: Path
```

用 `@dataclass(frozen=True)` 而非字典：字段有类型提示、IDE 能补全、`frozen` 防止运行期被误改（配置应当是不可变的）。

#### 代码段 3：缺失凭据的明确报错

```python
missing = [
    name
    for name, value in (("BAIDU_API_KEY", api_key), ("BAIDU_SECRET_KEY", secret_key))
    if not value
]
if missing:
    raise ConfigError(
        "缺少配置项：" + "、".join(missing) + "\n\n"
        "请将 .env.example 复制为 .env，并填入百度智能云控制台应用的 API Key 与 Secret Key。\n"
        "获取方式：百度智能云控制台 → 人脸识别 → 创建应用。"
    )
```

不满足于"KeyError: 'BAIDU_API_KEY'"，而是给出**缺失了哪几项**以及**去哪里申请**。这条消息会原样显示在启动错误对话框里。

#### 代码段 4：阈值解析

```python
def _parse_threshold(raw: str) -> int:
    if not raw.strip():
        return DEFAULT_MATCH_THRESHOLD        # 80，百度官方推荐值
    try:
        value = int(float(raw))
    except ValueError:
        raise ConfigError(f"MATCH_THRESHOLD 必须是数字，当前值为：{raw!r}") from None
    if not 0 <= value <= 100:
        raise ConfigError(f"MATCH_THRESHOLD 必须在 0~100 之间，当前值为：{value}")
    return value
```

先 `float` 再 `int`：容忍用户写成 `80.0`。`from None` 抑制异常链，让使用者只看得到自己的错误说明而不是 Python 内部 traceback。

#### 代码段 5：控制等级解析

```python
def _parse_control(raw: str, name: str, default: str) -> str:
    value = raw.strip().upper() or default
    if value not in CONTROL_LEVELS:          # ("NONE","LOW","NORMAL","HIGH")
        raise ConfigError(f"{name} 只能是 {'/'.join(CONTROL_LEVELS)} 之一，当前值为：{raw!r}")
    return value
```

`.upper()` 容忍小写输入；错误消息里动态列出合法取值，用户不用翻文档就知道该怎么改。

### 4.2 `core/errors.py` — 错误码映射（176 行）

**职责**：把百度返回的数字错误码翻译成"人话"，并把异常分成两类。

#### 代码段 1：用集合声明需要特殊处理的码

```python
TOKEN_INVALID = 110
TOKEN_EXPIRED = 111
NO_MATCH_USER = 222207      # 1:N 检索未找到匹配用户 —— 正常业务结果，不是故障
USER_NOT_EXIST = 223103
FACE_NOT_EXIST = 223106
GROUP_NOT_EXIST = 223100
GROUP_ALREADY_EXIST = 223101

_TOKEN_ERRORS = frozenset({TOKEN_INVALID, TOKEN_EXPIRED})
_QUOTA_ERRORS = frozenset({17, 18, 19})
```

**`222207` 是最关键的一个**：它在协议层是"错误码"，但业务上是"没找到人"——等同陌生人。把它和真正的故障区分开，是"陌生人判断"能正确工作的前提。

#### 代码段 2：分类的提示文案

```python
_QUALITY_MESSAGES = {
    223113: "人脸有遮挡。请勿遮挡面部后重拍。",
    223114: "人脸模糊。拍摄时请保持稳定，避免晃动。",
    223115: "人脸光照不佳。请到光线适宜的地方拍摄。",
    223116: "人脸不完整。请将完整的人脸移入画面内。",
    223120: "活体检测未通过，照片中的人脸疑似二次翻拍。请拍摄真人。",
    ...
}
```

质量类错误码（`223113`–`223131`）逐条给具体原因和**可操作的补救建议**，而不是笼统的"识别失败"。用户看到后知道下一步该做什么。

#### 代码段 3：兜底不丢信息

```python
def friendly_message(code: int, raw_message: str = "") -> str:
    known = ERROR_MESSAGES.get(code)
    if known:
        return known
    if raw_message:
        return f"接口返回错误（{code}）：{raw_message}"
    return f"接口返回未知错误（{code}）。"
```

遇到没收录的错误码，**保留原始错误码和消息**，而不是显示"未知错误"——否则排查时没有任何线索。

#### 代码段 4：两类异常分开

```python
class FaceAPIError(Exception):
    """百度接口返回了非零 error_code。"""
    def __init__(self, code: int, raw_message: str = "") -> None:
        self.code = code
        self.raw_message = raw_message
        self.friendly = friendly_message(code, raw_message)
        super().__init__(f"[{code}] {raw_message or self.friendly}")

class FaceNetworkError(Exception):
    """请求未能拿到响应：超时、连接失败等。"""
```

**为什么要分成两个类**：识别失败时，如果是网络问题却报"陌生人"，是把故障当成了业务结论。分成两类后，界面层可以保证"网络失败绝不会被误报为陌生人"（见 [4.11](#411-recognize_tabpy--单人识别页-225-行)）。

#### 代码段 5：跨模块的异常描述函数

```python
def describe_exception(exc: BaseException) -> str:
    if isinstance(exc, (FaceAPIError, FaceNetworkError)):
        return exc.friendly
    if isinstance(exc, ValueError) and str(exc):
        # ImageEncodeError 等本地校验类错误，消息本身已是可读中文
        return str(exc)
    return f"发生未预期的错误：{exc}"
```

放在 `errors.py` 而不是界面层，是为了让各页签都能直接 import。这里用 `isinstance(exc, ValueError)` 而不是 import `ImageEncodeError`，**刻意避免循环依赖**（`ImageEncodeError` 定义在 `images.py`，而 `images.py` 不该依赖 `errors.py`）。

### 4.3 `core/images.py` — 图片读写（113 行）

**职责**：全项目所有图片文件读写的唯一入口，以及"转成百度要的 Base64"。

#### 代码段 1：为什么必须有这个模块

```python
"""图片读写辅助。

**不要使用 `cv2.imread` / `cv2.imwrite`。**
它们在 Windows 上无法处理含非 ASCII 字符的路径——文件明明存在，
`cv2.imread` 却返回 None，`cv2.imwrite` 则静默失败。中文文件名和中文用户目录
（如 `C:\\Users\\张三\\Pictures\\`）在这里都非常常见，所以统一改走：

    读：path.read_bytes() → np.frombuffer → cv2.imdecode
    写：cv2.imencode → path.write_bytes()
"""
```

这是**实测踩出来的坑**。项目自带的测试图 `作业10.jpg` 就是中文名，`cv2.imread` 直接返回 `None`。改成"Python 读字节 + `imdecode`"后正常。

#### 代码段 2：安全的读图

```python
def load_bgr_image(source: str | Path | np.ndarray) -> np.ndarray:
    if isinstance(source, np.ndarray):
        if source.size == 0:
            raise ImageEncodeError("图像数据为空，请重新采集。")
        return source                      # 摄像头帧直接返回

    path = Path(source)
    if not path.exists():
        raise ImageEncodeError(f"图片文件不存在：{path}")

    suffix = path.suffix.lower()
    if suffix not in SUPPORTED_SUFFIXES:   # .png/.jpg/.jpeg/.bmp
        readable = "、".join(sorted(s.lstrip(".").upper() for s in SUPPORTED_SUFFIXES))
        raise ImageEncodeError(
            f"不支持的图片格式：{suffix or '（无扩展名）'}。仅支持 {readable}，不支持 GIF。"
        )

    buffer = np.frombuffer(path.read_bytes(), dtype=np.uint8)
    frame = cv2.imdecode(buffer, cv2.IMREAD_COLOR)
    if frame is None:
        raise ImageEncodeError(f"无法解析该图片文件（可能已损坏）：{path.name}")
    return frame
```

三重保护：**扩展名白名单**（在本地就拒掉 GIF，不浪费一次网络请求）→ **中文路径安全读取** → **解码失败检测**。

#### 代码段 3：安全的写图

```python
def save_bgr_image(frame: np.ndarray, path: str | Path, quality: int = 95) -> bool:
    try:
        target = Path(path)
        target.parent.mkdir(parents=True, exist_ok=True)
        ok, buffer = cv2.imencode(".jpg", frame, [int(cv2.IMWRITE_JPEG_QUALITY), quality])
        if not ok:
            return False
        target.write_bytes(buffer.tobytes())
        return True
    except Exception:
        return False
```

同样是 `imencode` + `write_bytes`。返回 `bool` 而非抛异常——照片保存失败不应导致注册整体失败（注册已经成功了）。

#### 代码段 4：自动降质的 Base64 编码

```python
def _encode_bgr(frame: np.ndarray) -> str:
    attempts = [(None, quality) for quality in (90, 80, 70)]
    attempts.append((MAX_IMAGE_SIDE, 80))    # 1920，降分辨率
    attempts.append((MAX_IMAGE_SIDE, 65))

    last_size = 0
    for max_side, quality in attempts:
        image = frame
        if max_side is not None:
            height, width = frame.shape[:2]
            longest = max(height, width)
            if longest > max_side:
                scale = max_side / longest
                image = cv2.resize(frame, (max(1, int(width*scale)), max(1, int(height*scale))),
                                   interpolation=cv2.INTER_AREA)
        ok, buffer = cv2.imencode(".jpg", image, [int(cv2.IMWRITE_JPEG_QUALITY), quality])
        if not ok:
            continue
        encoded = base64.b64encode(buffer.tobytes()).decode("ascii")
        last_size = len(encoded)
        if last_size <= MAX_BASE64_BYTES:    # 2 MB
            return encoded

    raise ImageEncodeError(
        f"图片过大，压缩后仍为 {last_size / 1024 / 1024:.1f}M，超出接口 2M 限制。"
        "请换一张分辨率更低的照片。"
    )
```

百度要求 Base64 后 **小于 2 MB**。这里采用**渐进降质**策略：先试高质量，超限再降 JPEG 质量，还超就缩分辨率。最坏情况给出明确的尺寸提示，而不是让接口返回一个费解的错误码。

注意 `base64.b64encode(...)` 的结果**不带** `data:image/jpg;base64,` 前缀——百度明确要求不能带。

### 4.4 `core/identity.py` — 姓名到 user_id 的派生（44 行）

**职责**：把任意中文姓名映射成百度允许的 `user_id`。

#### 代码段 1：派生函数

```python
USER_ID_PREFIX = "u"
_HASH_LENGTH = 16

def derive_user_id(name: str) -> str:
    """由姓名确定性地派生出一个合法的云端 user_id（共 17 字符）。"""
    digest = hashlib.md5(name.strip().encode("utf-8")).hexdigest()
    return USER_ID_PREFIX + digest[:_HASH_LENGTH]
```

**为什么必须派生**：百度的 `user_id` 只允许**数字、字母、下划线**且 ≤48 字节，中文姓名（UTF-8 下"张三"占 6 字节）不能直接用。

**为什么用 MD5 而不是自增 ID 或拼音**：

| 方案         | 问题                               |
| ---------- | -------------------------------- |
| 自增 ID      | 无法做到"按姓名判重"，同名注册会创建两个用户          |
| 拼音         | "张三"和"章三"都变 `zhangsan`，重名歧义      |
| **MD5 派生** | 同名 → 同 `user_id`（幂等），不同名 → 不同 ID |

同名映射到同一个 `user_id` 之后，就能用上百度的 **`action_type=APPEND`**——同一用户下最多存 20 张人脸。同一个人换个角度再注册一张，识别命中率随之提高。这是整个设计里"用中文姓名也能工作"的关键一环。

中文姓名本身通过百度 `user_info` 字段承载（上限 256 字节，支持 UTF-8）。

#### 代码段 2：自测

```python
def _self_test() -> None:

        user_id = derive_user_id(name)
        assert user_id.isascii(), f"{name} 派生出非 ASCII user_id"
        assert all(c.isalnum() or c == "_" for c in user_id), f"{name} 含非法字符"
        assert len(user_id) <= 48, f"{name} 的 user_id 超长"

    assert derive_user_id("张三") == derive_user_id("张三")      # 稳定性
    assert derive_user_id("  张三  ") == derive_user_id("张三")  # 空白无关
    assert derive_user_id("张三") != derive_user_id("李四")      # 不碰撞
```

断言的就是"合法性、确定性、唯一性"三个不变式，运行 `python core/identity.py` 即可验证。

#### 代码段 2：每操作一个连接

```python
@contextmanager
def _connect(self) -> Iterator[sqlite3.Connection]:
    conn = sqlite3.connect(self.db_path, timeout=10)
    conn.row_factory = sqlite3.Row
    try:
        yield conn
        conn.commit()
    except Exception:
        conn.rollback()
        raise
    finally:
        conn.close()
```

**为什么不用一个长连接**：SQLite 的连接默认不能跨线程共享（`check_same_thread`），而本项目会在工作线程里读数据库。每次操作开关连接是最简单且线程安全的做法——SQLite 的单次连接开销极小。`timeout=10` 让并发写入时等待锁而不是立刻报 `database is locked`。

`row_factory = sqlite3.Row` 让结果可以按列名取值（`row["name"]`），比下标可读。

#### 代码段 3：幂等的 upsert

```python
def upsert_person(self, user_id, name, group_id, face_token, photo_path) -> Person:
    now = _now()
    with self._connect() as conn:
        existing = conn.execute(
            "SELECT created_at FROM persons WHERE user_id = ?", (user_id,)
        ).fetchone()
        if existing is None:
            conn.execute("INSERT INTO persons (...) VALUES (?, ?, ?, ?, ?, ?, ?)",
                         (user_id, name, group_id, face_token, photo_path, now, now))
        else:
            conn.execute("UPDATE persons SET name=?, group_id=?, face_token=?, "
                         "photo_path=?, updated_at=? WHERE user_id=?",
                         (name, group_id, face_token, photo_path, now, user_id))
    person = self.get_person(user_id)
    assert person is not None
    return person
```

**关键点：更新分支保留 `created_at`**。同名二次注册时刷新 `face_token` / 照片 / `updated_at`，但首次注册时间不变——"注册时间"在语义上就该是第一次的时间。

### 4.6 `core/camera.py` — 摄像头采集线程（189 行）

#### 代码段 1：Windows 后端选择

```python
def _open_capture(index: int) -> cv2.VideoCapture | None:
```

#### 代码段 2：容量为 1 的帧队列（防积压）

```python
def _publish(self, frame: np.ndarray) -> None:
    """写入最新帧；队列满则丢掉旧帧再放，保证不留积压。"""
    try:
        self._queue.put_nowait(frame)
        return
    except queue.Full:
        pass
    try:
        self._queue.get_nowait()       # 丢弃最旧的一帧
    except queue.Empty:
        pass
    try:
        self._queue.put_nowait(frame)
    except queue.Full:
        pass
```

队列 `maxsize=1`。摄像头以 30 FPS 产帧，界面以 30 FPS 消费——一旦某帧处理慢，积压的旧帧会让画面延迟越来越大。**丢旧帧**保证界面永远显示最新画面。（已用合成数据验证：连推 5 帧后取到的是第 5 帧。）

#### 代码段 4：线程生命周期

```python
def start(self) -> None:
    if self._thread is not None and self._thread.is_alive():
        return                                        # 幂等
    self._stop_event.clear()
    self._set_state("starting")
    self._thread = threading.Thread(target=self._run, name="camera-stream", daemon=True)
    self._thread.start()

def stop(self, timeout: float = 2.0) -> None:
    self._stop_event.set()
    thread = self._thread
    if thread is not None and thread.is_alive():
        thread.join(timeout=timeout)
    self._thread = None
    self._drain()
    if self.state != "failed":
        self._set_state("idle")
```

`daemon=True` 保证主程序退出时线程不会吊住进程；`stop()` 用 `Event` 通知 + `join` 等待 + 在 `finally` 里 `release()` 设备，确保不残留占用。

```python
# 1.05 秒的间隔在人工交互中几乎无感，却能稳定规避这个自伤式的失败。
MIN_REQUEST_INTERVAL_SECONDS = 1.05
```

#### 代码段 2：限流器

```python
def _throttle(self) -> None:
    """把连续请求拉开到 MIN_REQUEST_INTERVAL_SECONDS 以上。

    在锁内 sleep 是有意为之：多个工作线程同时发请求时，这里会把它们串行化，
    正好符合"全局限速"的语义。
    """
    with self._throttle_lock:
        wait = self._last_request_at + MIN_REQUEST_INTERVAL_SECONDS - time.monotonic()
        if wait > 0:
            time.sleep(wait)
        self._last_request_at = time.monotonic()
```

**为什么必须有**：免费额度是 **1 QPS**。实测中"注册后立刻识别"连续两次调用直接触发错误码 `18`。在锁内 sleep 看起来会阻塞其他线程，但这正是想要的——全局限速。

用 `time.monotonic()` 而非 `time.time()`：前者是单调时钟，不受系统时间调整影响。

#### 代码段 3：防止密钥泄漏的错误信息

```python
def _brief_error(exc: requests.RequestException) -> str:
    """把 requests 异常压缩成一句简短原因。

    绝不能直接使用 `str(exc)`：它包含完整请求 URL，而取 token 的 URL 里带着
    `client_secret`，一旦原样显示在界面上或写进日志就等于泄露 SK。
    """
    if isinstance(exc, requests.Timeout):
        return "请求超时"
    if isinstance(exc, requests.ConnectionError):
        return "无法连接到百度服务器"
    return exc.__class__.__name__
```

**这是一个真实的安全缺陷修复**。原本直接拼接 `str(exc)`，结果取 token 失败时，错误消息里赫然出现 `?...&client_secret=你的真实SK`——这句话会弹到界面对话框上。压缩成一个短句后，消息从 400+ 字符降到 49 字符，且不含任何凭据。

#### 代码段 5：请求重试与错误分流

```python
def _post(self, path: str, payload: dict) -> dict:
    """发起业务请求。token 失效时清缓存重取并重试一次。"""
    last_error: FaceAPIError | None = None

    for attempt in (0, 1):
        token = self._get_access_token(force_refresh=attempt == 1)   # 第二次强制刷新
        self._throttle()
        try:
            response = self._session.post(f"{API_BASE}{path}",
                                          params={"access_token": token},
                                          json=payload, timeout=self._timeout)
        except requests.RequestException as exc:
            raise FaceNetworkError(_brief_error(exc)) from exc

        try:
            data = response.json()
        except ValueError:
            raise FaceNetworkError(
                f"接口返回了无法解析的内容（HTTP {response.status_code})") from None

        code = int(data.get("error_code", 0))
        if code == 0:
            return data

        error = FaceAPIError(code, str(data.get("error_msg", "")))
        # 仅 token 失效类错误值得重试；其余直接抛出，避免浪费配额
        if attempt == 0 and is_token_error(code):
            last_error = error
            continue
        raise error

    assert last_error is not None
    raise last_error
```

**只对 token 失效（110/111）重试一次**。如果对任何错误都重试，一个"照片中没有人脸"的失败会白白多发一次请求，在 1000 次/月的额度下是浪费。

#### 代码段 6：解包 `result` —— 最关键的一处修复

```python
@staticmethod
def _result_of(data: dict) -> dict:
    """取出响应中的 `result` 载荷。

    人脸 v3 接口在成功时把业务数据包在 `result` 里，而不是放在顶层：

        {"error_code": 0, "error_msg": "SUCCESS",
         "result": {"face_token": "...", "user_list": [...]}}

    部分接口（如删除人员）成功时 `result` 为 null，因此统一归一化为空字典。
    顶层直接取 `face_token` / `user_list` 会永远取到空值，导致检索结果恒为空、
    所有人都被判成"陌生人"。
    """
    result = data.get("result")
    return result if isinstance(result, dict) else {}
```

**这是全项目最重要的一处修复**。最初的实现从顶层取 `data.get("face_token")` \ `data.get("user_list")`——**永远取到空值**。后果是：

- `face_token` 存进档案是空的
- `/search` 的结果恒为空列表 → **所有人都被判成"陌生人"，识别功能完全失效**

而且这个 bug 在单元测试里看不出来（用桩件时返回的是自己造的假数据），只有打**真实接口**导出原始 JSON 才会暴露。

```python
    # 摄像头是异步启动的：状态可能在页签打开之后才变为 running，
    # 因此在轮询里同步状态，而不是只在页签显示时同步一次。
    state = self._app.camera.state
    if state != self._last_camera_state:
        self._last_camera_state = state
        if self._on_camera_state is not None:
            try:
                self._on_camera_state(state)
            except tk.TclError:
                pass

    if self._mode == "live":
        frame = self._app.camera.read()
        if frame is not None:
            self._last_live = frame
        if frame is not None or self._last_live is not None:
            self._render(self._last_live)      # 保持上一帧，避免闪烁
        else:
            self._render_placeholder()
    self._after_id = self.after(REFRESH_INTERVAL_MS, self._tick)   # 33ms ≈ 30 FPS
```

**这里修掉了一个真实的时序 bug**：最初只在页签显示时同步一次抓拍按钮状态。但摄像头是异步启动的——如果用户在人脸识别页签打开时摄像头还没就绪，按钮会被永久禁用，即使摄像头随后启动成功也不会恢复。改成在轮询里检测状态**变化**才回调，就自愈了。

### 4.10 `ui/main_window.py` — 主窗口（227 行）

**职责**：三页签容器 + 状态栏 + **跨页签共用的异步机制**。

#### 代码段 1：为什么用队列而不是 `after(0)`

```python
"""...
为什么用队列而不是在工作线程里直接 `root.after(0, ...)`：
`after()` 会调用 Tcl 的 `createcommand`，而 Tcl 解释器只允许主线程操作它。
当主线程不在 `mainloop()` 内部时（例如单测里用 `update()` 驱动事件循环），
从工作线程调用 `after` 会直接抛 `RuntimeError: main thread is not in main loop`。
改成"工作线程只往 Queue 里放结果，主线程定时轮询取出并执行回调"，
既保证回调始终在主线程执行，也不依赖主线程此刻是否卡在 mainloop 里。
"""
```

这是**实现过程中实测发现的缺陷**：最初的写法就是教科书式的 `self.after(0, callback)`，在跑集成测试时炸出 `RuntimeError`。

#### 代码段 2：异步执行 + 结果泵

```python
def run_in_background(self, work, on_success=None, on_error=None) -> None:
    """在工作线程执行 work()，回调一律在主线程执行。"""
    def runner() -> None:
        try:
            result = work()
        except BaseException as exc:          # 工作线程必须兜住一切
            self._result_queue.put(("error", exc, on_error))
        else:
            self._result_queue.put(("ok", result, on_success))

    threading.Thread(target=runner, daemon=True).start()
```

```python
def _poll_results(self) -> None:
    """主线程侧的结果泵：取出工作线程的结果并执行回调。"""
    while True:
        try:
            kind, payload, callback = self._result_queue.get_nowait()
        except queue.Empty:
            break
        try:
            if kind == "error":
                if callback is not None:
                    callback(payload)
                else:
                    self.show_error(describe_exception(payload))
            elif callback is not None:
                callback(payload)
        except Exception:
            # 回调本身出错不能拖垮结果泵，否则后续结果全部堵死
            traceback.print_exc()
            self.status("界面更新时发生错误，详情见控制台。")

    self._poll_id = self.after(RESULT_POLL_MS, self._poll_results)   # 每 40ms 一次
```

工作线程**从不触碰 Tk**，只往队列里放三元组；主线程每 40ms 清空一次队列并执行回调。回调自身抛异常时被单独捕获——否则一次回调失败会让 `after` 循环中断，此后所有结果都堵在队列里无人处理。

`on_error` 为 `None` 时走默认分支，自动把异常翻译成中文提示——调用方只在需要自定义错误处理时才传。

#### 代码段 3：页签切换时停止其他预览

```python

    """只让当前可见页签的预览轮询取帧。

    两个页签同时轮询会争抢容量为 1 的帧队列，导致两边都频繁拿到 None，
    因此切换时必须停掉其他页签的预览。
    """

        current = self._current_tab()
    except Exception:
        return
```

#### 代码段 4：忙碌状态与异常兜底

```python
def _on_recognize(self) -> None:
    frame = self.preview_widget.current_frame()
    if frame is None:
        self.app.show_warning("请先点击「抓拍当前画面」或「选择文件」提供一张待识别照片。", "缺少待识别图片")

    self.app.set_busy(self.recognize_btn, True, "识别中…")
    self._reset_result(show_placeholder=False)
    self.app.status("正在识别…")

    def work():
        return self.app.client.search(frame, group_id, threshold)

    def done(candidates: list[dict]) -> None:
        self.app.set_busy(self.recognize_btn, False)
        if not candidates:
            # 云端未返回任何候选：可能是无人脸，也可能是分数全部低于阈值
            self._show_stranger(threshold, best_score=None)
            return
        best = candidates[0]
        if best["score"] < threshold:
            self._show_stranger(threshold, best_score=best["score"])
        else:
            self._show_match(best, threshold)

    def failed(exc: BaseException) -> None:
        # 网络/配额等失败必须与"陌生人"区分开，否则会把故障误报成没认出人
        self.app.set_busy(self.recognize_btn, False)
        self._reset_result(show_placeholder=True)
        self.app.show_error(describe_exception(exc))

    self.app.run_in_background(work, done, failed)
```

**三道判定，对应需求的三种情况**：

| 情况                | 分支                           | 结果             |
| ----------------- | ---------------------------- | -------------- |
| 有候选且 `score ≥ 阈值` | `_show_match`                | 显示姓名 + 相似度     |
| 有候选但 `score < 阈值` | `_show_stranger(best_score)` | 陌生人 + 说明差多少分   |
| 无任何候选             | `_show_stranger(None)`       | 陌生人 + 未找到匹配项   |
| 网络/配额失败           | `failed`                     | **报错，绝不显示陌生人** |

最后一行是**规格明确要求的**：把网络故障报成"陌生人"等于把系统故障伪装成业务结论，会让用户误以为"这人没注册过"。

**顺序至关重要**：先删云端，成功后才删本地。如果反过来，云端删除失败时本地记录已经没了——用户会以为删干净了，实际上云端还在，下次识别照样匹配到这个人。这是最糟的一类不一致。

```python

    # 云端删除失败：本地档案保留，提示用户重试
    self.app.set_busy(self.delete_btn, False)
    self.app.show_error(
        f"{describe_exception(exc)}\n\n"
        f"「{person.name}」的本地记录已保留，可在网络恢复后重试删除。"
    )
```

错误提示里明确告诉用户"记录已保留、可以重试"——而不是让人担心数据是不是删了一半。

```python
        settings = load_config()

        _show_fatal("配置有误", str(exc))
        return 1                        # 退出码 1

    try:
        store = PersonStore(settings.db_path)
    except Exception as exc:
        traceback.print_exc()
        _show_fatal("无法打开本地数据库", f"初始化档案数据库失败：{exc}")
        return 1

    client = BaiduFaceClient(settings.api_key, settings.secret_key)
    camera = CameraStream()

    try:
        window = MainWindow(settings, store, client, camera)
    except Exception as exc:
        traceback.print_exc()
        client.close()
        camera.stop()
        _show_fatal("启动失败", f"界面初始化失败：{exc}")
        return 1

    try:
        window.mainloop()
    except KeyboardInterrupt:
        pass
    return 0
```

## 五、关键技术专题

### 5.1 百度人脸 V3 接口契约要点

| 项            | 内容                                                                                              |
| ------------ | ----------------------------------------------------------------------------------------------- |
| 鉴权           | `POST /oauth/2.0/token`，`grant_type=client_credentials` + AK/SK，返回的 `access_token` **有效期 30 天** |
| 凭据位置         | 业务请求把 `access_token` 放在 **URL query**，不是 Header                                                 |
| 请求体          | `Content-Type: application/json`，统一 POST                                                        |
| 图片           | `image_type=BASE64`，**不带** `data:image/jpg;base64,` 前缀，编码后 <2 MB                                |
| **响应结构**     | 成功时业务数据包在 **`result`** 字段里 —— 这是最容易踩的坑，见 [4.7 代码段 6](#代码段-6解包-result--最关键的一处修复)                 |
| `user_id` 约束 | 仅数字/字母/下划线，≤48 字节 → 中文姓名必须派生                                                                    |
| 配额           | 免费额度约 1 QPS、1000 次/月，超出返回 `17`/`18`/`19`                                                        |
| 同步延迟         | 注册约 5 秒生效；**删除后检索索引同步可能还要几秒**                                                                   |
| 人脸上限         | 每个 `user_id` 最多 20 张脸（因此追加式注册能提升命中率）                                                            |

### 5.2 线程模型

Tkinter 是**单线程**的——所有界面操作必须在主线程。

```
主线程（Tkinter mainloop）
├── after(33ms)  → preview._tick       取摄像头帧 → 转 PhotoImage → 刷新 Label
├── after(40ms)  → main_window._poll_results   清空结果队列 → 执行回调
└── 按钮回调      → 只做本地校验 + set_busy + run_in_background

工作线程（daemon，每请求一个）
└── work()  → HTTP 请求 / 照片落盘 / 读写 SQLite
            → 结果放进 _result_queue（绝不触碰 Tk）
```

**三条铁律**：

1. 按钮回调里**绝不直接发请求** —— 否则界面冻结
2. 工作线程**绝不触碰 Tk** —— 否则 `RuntimeError: main thread is not in main loop`
3. 所有界面更新都在主线程的结果泵里执行

已实测验证：慢请求（1.2 秒）期间主线程心跳仍有 39 次/秒，界面未阻塞；按钮处于 `disabled` 状态不可重复点击。

### 5.3 错误处理分层

```
百度错误码（数字）
      ↓  core/errors.friendly_message
中文可读提示（含具体原因 + 补救建议）
      ↓  core/errors.FaceAPIError / FaceNetworkError
带分类的异常对象
      ↓  core/errors.describe_exception
界面层统一的一句话
      ↓  main_window.show_error
对话框 + 状态栏
```

**分层的意义**：业务代码只管抛异常，界面只管显示。新增一个错误码只需在 `errors.py` 的映射表里加一行，全应用自动生效。

### 5.4 中文路径问题

Windows 上 `cv2.imread` / `cv2.imwrite` **不支持非 ASCII 路径**——文件存在却返回 `None`，或者静默写入失败。

| 操作  | 不安全                      | 本项目采用                                                  |
| --- | ------------------------ | ------------------------------------------------------ |
| 读   | `cv2.imread(path)`       | `path.read_bytes()` → `np.frombuffer` → `cv2.imdecode` |
| 写   | `cv2.imwrite(path, img)` | `cv2.imencode` → `path.write_bytes()`                  |

全部集中在 [core/images.py](core/images.py)。实测：`cv2.imread('作业10.jpg')` 返回 `None`，而 `load_bgr_image('作业10.jpg')` 正常解码出 1706×1279。

### 5.5 姓名到 user_id 的派生

```
"张三"  →  MD5(UTF-8 字节)  →  hexdigest  →  取前 16 位  →  加前缀 "u"
        →  "u615db57aa314529a"
```

**三个性质**：合法（纯 ASCII、17 字符 < 48）、确定（同名恒等）、唯一（异名不同）。

**业务价值**：同名 → 同 `user_id` → 可用 `APPEND` 累积最多 20 张人脸 → 识别命中率提升。

### 5.6 数据一致性策略

| 操作   | 权威来源 | 策略                        |
| ---- | ---- | ------------------------- |
| 注册   | 云端   | 云端成功后才写本地档案；云端失败本地不留痕     |
| 删除   | 云端   | 云端成功后才删本地；云端失败**保留本地**并报错 |
| 列表展示 | 本地   | 只读本地库，避免逐行调接口耗尽配额         |
| 明细查询 | 云端   | 仅在选中某行时查询；失败只影响明细区        |
| 姓名显示 | 云端优先 | 云端 `user_info` 为空时回退本地档案  |

核心原则：**不能出现"本地以为删了、云端还在"**。悲观地保留本地记录让人重试，好过制造假的一致。
